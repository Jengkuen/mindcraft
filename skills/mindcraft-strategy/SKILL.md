# Guide strategy

Resolve the personal instance through `../../AGENTS.md`. Follow its authority rules. Read the live `netherite/README.md`, `netherite/current-week.md` and `netherite/ingest.md` relative to that instance, never the blank starter copies.

## Recover before reviewing

Recover the current plan's approval state, known constraints and saved review position. Resume the first unresolved item. Do not repeat questions already answered or interpret last week's plan as approved for this week.

Follow project links for the scope of the requested review. For a full review, traverse every registered project and its `## Workstreams` and nested `#### Tasks` sections before claiming completeness. Follow workspace controls for current evidence as needed; label any inaccessible or unchecked scope. Do not claim to have inspected atomic tasks merely from the operating views.

Reconcile reported progress, actual evidence, deadlines, waiting states and capacity. Keep user reports distinct from independently checked outputs. Read relevant Bedrock context only when it changes judgment. Surface stale or missing records without assuming that the real-world work has stopped.

## Carry the sequence

Review one decision at a time when guiding the user. For each relevant workstream, establish its current state and the next useful outcome, explicit deferral, or waiting dependency. Help define a reasonable stopping point rather than letting the user design the process from scratch.

Propose a concrete milestone, next action, finish condition and effort budget. Include dependencies or genuine deadlines. Keep proposed allocations separate from approved commitments. An effort budget is not a calendar event, elapsed work or a claim of availability.

Treat queued ideas as possibilities. Ask before adopting one or materially changing scope. If the user directly requests and approves a particular change, apply that authority without another generic confirmation. Honour explicit overrides and genuine urgent changes rather than enforcing a rigid weekly strategy day.

After each substantive decision, save it in its canonical project/control and update a short weekly pointer or decision note. Persist the next unresolved item so another session can resume. Do not wait until the entire review finishes to save useful state.

## Make execution navigable

For an approved new execution project, create only what is needed:

- A registry link in `netherite/README.md`.
- `netherite/projects/<project>.md` with outcome, status, workspace link, `## Workstreams` and a nested `#### Tasks` section per workstream.
- A workspace README and workstream control matching `../../architecture.md`.
- Relevant Bedrock context only when it improves representation; no invented identity or goal is required.

Record approval scope and basis. Drafts remain proposed until adopted. Let workspace controls own detailed execution and Netherite own current management state.

## Agree and stop

Reconcile the proposed work with actual constraints and capacity. Present a compact plan including outcomes, budgets, finish conditions, deferrals and the first operation. Ask for the remaining substantive decision, then mark only the accepted scope approved.

Stop when the in-scope work has an agreed outcome or explicit defer/wait state, the allocation fits known capacity, and the next action is clear. If the user stops early, preserve the draft and next unresolved item. Do not block an explicitly authorised operation on finishing the whole review.

At review, optionally ask what helped, what hindered and what one adjustment to try. Record observations as observations; do not establish a recurring practice, reminder or new commitment without a decision. Finish by stating what is agreed, what remains undecided and where execution starts.
