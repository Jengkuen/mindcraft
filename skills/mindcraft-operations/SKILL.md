# Support operations

Resolve the personal instance through `../../AGENTS.md` and follow its authority rules. Read the live `netherite/current-week.md`, then follow the relevant project, workstream control and latest handoff. Read only context needed for the selected work.

## Capture an idea

For a capture-only request, append the date, idea, brief reason and genuine expiry/deadline to the live `netherite/ingest.md`. Preserve the user's wording where possible. Do not invent a deadline, create an active task, change the plan or start a strategy review. Acknowledge briefly and preserve the current operation. Surface an urgent expiry rather than silently waiting until next week's review.

## Recover and choose

Recover the actual result, unfinished work, blockers and next action from saved files. If the user only asks where things stand, report that state without silently changing the plan.

If the user selects a task within an approved boundary, proceed. Otherwise choose one bounded next action serving an agreed milestone, considering dependencies, deadlines and the available time. If substantive scope has not been approved, propose only the needed boundary using the strategy skill at `../mindcraft-strategy/SKILL.md`. A draft week does not prevent work explicitly authorised by the user.

Show a short work card in ordinary language: outcome, next action, done condition and stopping condition/timebox. Use the user's supplied timebox or propose one where it helps. Do not require the user to approve routine implementation choices within an already authorised task.

## Do the work

Execute or support the selected task. Ask for source material when it is needed; never invent evidence from an unavailable article, document or tool. Distinguish preparation from completion and user-reported results from checked output.

Resolve routine obstacles within scope. If blocked at an approval checkpoint or dependency, identify what is missing and the permitted next step. Do not cross the boundary to maintain momentum. Capture speculative redirections instead of reopening strategy, unless the user explicitly overrides or an urgent change requires attention.

When a task is verified complete, update it and continue through the approved workstream plan only if time and stopping conditions allow. Do not infer project/workstream closure, permission for external actions, or more time from task completion.

## Save a handoff

At a useful stopping point or explicit stop request:

1. Save artifacts and update the executing workstream control with the date, actual result, supporting evidence, unfinished work/blocker, and next action with its finish condition.
2. Mark task completion only when supported. Keep elapsed time unknown unless measured or supplied; an allocated timebox does not establish time spent.
3. Update the project's current management tasks if warranted. Link the latest handoff from `netherite/current-week.md` without copying the full history.
4. Preserve the current plan's approval state and saved strategy-review position. A handoff must not approve unrelated proposals or close the workstream.
5. Verify the saved state. If a write fails, report what is unsaved and provide the resumable content instead of claiming success.

Tell the user what happened, what remains and the next action. On a later session, use the saved evidence rather than relying on chat history. If records conflict, inspect dates and evidence and surface consequential uncertainty instead of inventing continuity.
